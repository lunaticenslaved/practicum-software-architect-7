# Задание 1. Исследование моделей и инфраструктуры для RAG-бота QuantumForge Software

## 1. Сравнение LLM-моделей

Для RAG-сценария LLM выполняет роль «пересказчика» найденного контекста. Основная точность ответа определяется качеством retrieval, а не генеративной моделью. Тем не менее, выбор LLM влияет на стоимость, безопасность и эксплуатационные риски.

### 1.1 Локальные модели (Hugging Face / Ollama)

**Рассматриваемые варианты:** Llama 3 (8B/70B), Mistral 7B, Qwen 2.5, Command R+ — с квантованием (Q4/Q5) или полные.

| Критерий | Оценка |
|----------|--------|
| **Качество ответов** | Современные open-source модели уровня Llama 3 70B при квантовании показывают качество, близкое к GPT-3.5 Turbo, и достаточное для суммаризации технической документации. Mistral 7B легче, но также пригоден. Для RAG-пересказа разница с облачными моделями некритична. |
| **Скорость работы** | На GPU (A100/T4) — 20–50 токенов/с. На CPU с квантованием (llama.cpp) — 5–15 токенов/с, что приемлемо для внутреннего инструмента с десятками одновременных пользователей. |
| **Стоимость владения** | Капитальные затраты на GPU-сервер (аренда выделенного сервера в Hetzner/Shadow: €200–600/мес) или собственное железо. При регулярном использовании и >1000 запросов/день локальное решение окупается за 6–12 месяцев по сравнению с API. |
| **Развёртывание** | Требует экспертизы: Docker-образы с vLLM или Ollama, управление памятью, квантование. Полный контроль над данными — ни один запрос не покидает контур компании. |

**Вывод:** Локальные модели — **стратегически верный выбор** для QuantumForge Software, учитывая конфиденциальность промышленной документации, требования SOC 2 и GDPR. Они обеспечивают полный контроль над данными и предсказуемую стоимость при масштабировании. Для MVP можно использовать Mistral 7B или Llama 3 8B в квантованном виде.

### 1.2 Облачные модели (OpenAI / YandexGPT)

| Критерий | Оценка |
|----------|--------|
| **Качество ответов** | GPT-4o — эталонное качество суммаризации. YandexGPT — силён в русскоязычных запросах, но QuantumForge — международная компания с документацией на английском и скандинавских языках. GPT-4o предпочтительнее. |
| **Скорость работы** | Высокая и стабильная, но зависит от загрузки API. Средняя латентность 1–3 секунды на запрос с контекстом среднего размера. |
| **Стоимость** | При среднем контексте 2000 токенов на запрос: ~$0.01–0.03 за ответ (GPT-4o). При 500 запросах/день — ~$150–450/мес. Для MVP приемлемо, но при масштабировании на всю компанию (200+ сотрудников) расходы вырастут кратно. |
| **Развёртывание** | Минимальные усилия — API-ключ и HTTP-интеграция. **Критический недостаток:** запросы уходят на серверы OpenAI в США, что создаёт риски для конфиденциальности промышленных данных и затрудняет прохождение SOC 2 аудита. |

**Вывод:** Облачные API удобны для прототипа, но **неприемлемы** для продакшена QuantumForge Software из-за регуляторных требований и характера данных (промышленные объекты, SCADA-интеграции). Руководство не может рисковать утечкой конфиденциальных спецификаций через внешнее API.

### 1.3 Промежуточный вариант: Self-hosted API (Azure OpenAI / Yandex Cloud)

Microsoft Azure OpenAI Service позволяет развернуть GPT-модели в своём тенанте с гарантиями обработки данных в EU-регионе. Yandex Cloud — аналогично для YandexGPT. Это компромисс между качеством облачных моделей и контролем над данными.

**Оценка:** Заслуживает рассмотрения, но добавляет зависимость от вендора и требует тщательного юридического анализа Data Processing Agreement. Стоимость выше, чем у pure-облака.

### 1.4 Итоговый выбор LLM

**Рекомендация: Локальная LLM (Mistral 7B или Llama 3 8B с квантованием Q4/Q5) через Ollama или vLLM.**

Обоснование:
- Полный контроль над данными — ключевое требование для SOC 2 и GDPR.
- Предсказуемая стоимость при масштабировании.
- Достаточное качество для RAG-сценариев.
- Возможность быстрой замены на более мощную модель (Llama 3 70B) при появлении GPU-инфраструктуры.
- Архитектурно RAG-пайплайн остаётся независимым от LLM — в будущем можно переключиться на любую модель.

## 2. Сравнение моделей эмбеддингов

Эмбеддинги — критический компонент RAG. От их качества напрямую зависит точность retrieval и, следовательно, всего бота. Для QuantumForge Software важна поддержка технической терминологии и многоязычность (английский, финский, шведский, эстонский).

### 2.1 Локальные Sentence-Transformers

**Рассматриваемые модели:** `BAAI/bge-large-en-v1.5`, `intfloat/multilingual-e5-large`, `all-MiniLM-L6-v2`.

| Критерий | Оценка |
|----------|--------|
| **Скорость индексации** | Высокая. ~21 000 документов индексируются за 15–40 минут на CPU (зависит от модели и длины чанков). На GPU — 5–10 минут. Отсутствие rate-limit позволяет массовую переиндексацию при необходимости. |
| **Качество поиска** | `bge-large-en` — лидер бенчмарка MTEB для английского языка. `multilingual-e5-large` — лучший выбор для мультиязычной среды QuantumForge. Обе модели показывают recall@10 >0.90 на технических корпусах. |
| **Стоимость** | Фиксированные инфраструктурные затраты (CPU/GPU-сервер). Нет платы за объём токенов. При росте базы на 400 стр./мес дополнительные затраты минимальны. |

**Вывод:** Локальные эмбеддинги — **оптимальный выбор**. `intfloat/multilingual-e5-large` покрывает скандинавские языки и английский, качество retrieval подтверждено бенчмарками, стоимость стабильна при росте.

### 2.2 Облачные эмбеддинги (OpenAI `text-embedding-3-large`)

| Критерий | Оценка |
|----------|--------|
| **Скорость индексации** | Ограничена rate-limit (3000 RPM для tier-1). Для 21 000 документов с разбиением на чанки (~100 000 чанков) потребуется 30+ минут и контроль лимитов. Переиндексация — боль. |
| **Качество поиска** | Высокое, модель универсальна. Но не имеет доменной специализации на технический язык. |
| **Стоимость** | $0.13 за 1M токенов. Для 100 000 чанков по 512 токенов: ~$6.50 за индексацию, но ежемесячные обновления (400 стр. ≈ 2000 новых чанков) добавляют расходы. При масштабировании стоимость растёт линейно. |

**Вывод:** Облачные эмбеддинги удобны для прототипа, но для регулярно обновляемой базы QuantumForge и требований конфиденциальности уступают локальным.

### 2.3 Итоговый выбор эмбеддингов

**Рекомендация:** `intfloat/multilingual-e5-large` (локально) с fallback на `BAAI/bge-large-en-v1.5` для англоязычных материалов.

Обоснование:
- Мультиязычность критична для финско-эстонской компании с документацией на нескольких языках.
- Локальное развёртывание = отсутствие утечек данных.
- Фиксированная стоимость, не зависящая от объёма запросов.
- Простая интеграция в CI/CD для автоматической реиндексации при обновлении документации.

## 3. Сравнение векторных баз: ChromaDB vs FAISS

### 3.1 ChromaDB

**Архитектура:** Клиент-серверная (Python/JS-клиент + сервер на FastAPI). Поддерживает SQLite (dev) и PostgreSQL (production). Встроенное хранение метаданных, фильтрация, пространства имён.

| Критерий | Оценка |
|----------|--------|
| **Скорость поиска** | Высокая для объёмов до 1M векторов благодаря HNSW-индексу. Для 100 000 чанков QuantumForge — запас по производительности кратный. |
| **Сложность внедрения** | Низкая на старте (`pip install chromadb`). Для продакшена требует отдельного сервиса и PostgreSQL. |
| **Удобство** | Встроенный API для CRUD-операций с документами, хранение метаданных из коробки, REST API для микросервисной архитектуры. |
| **Инкрементальные обновления** | Поддерживает добавление/удаление отдельных векторов без пересборки индекса — ключевое преимущество при ~400 новых страницах в месяц. |
| **Стоимость владения** | Требует отдельный контейнер, сетевые взаимодействия, администрирование БД (backup, мониторинг). |

### 3.2 FAISS

**Архитектура:** Библиотека Facebook Research. Работает как in-memory индекс в процессе приложения. Нет встроенного сервера, клиента или хранилища метаданных.

| Критерий | Оценка |
|----------|--------|
| **Скорость поиска** | Экстремально высокая за счёт прямого доступа к памяти. Оптимально для низколатентных сценариев. |
| **Сложность внедрения** | Низкая на старте (библиотека в коде). Но всё управление метаданными, персистентностью и обновлениями ложится на разработчика. |
| **Удобство** | Неудобна для частых обновлений: стандартный IndexIVF требует пересборки при добавлении данных. IndexIDMap позволяет добавлять, но с деградацией точности. |
| **Инкрементальные обновления** | Ограничены. Для ежемесячного пополнения на 400 страниц потребуется регулярная пересборка индекса, что неудобно для CI/CD и оперативного доступа к свежей документации. |
| **Стоимость владения** | Минимальная: CPU + RAM. Нет отдельного сервиса для администрирования. |

### 3.3 Сравнительная таблица

| Характеристика | ChromaDB | FAISS |
|---------------|----------|-------|
| Инкрементальные обновления | ✅ Полная поддержка | ⚠️ Ограничена |
| Метаданные | ✅ Встроенные | ❌ Самостоятельно |
| Восстановление после сбоя | ✅ Персистентность | ⚠️ Собственная реализация |
| Микросервисная архитектура | ✅ REST API | ❌ In-process |
| Простота MVP | ✅ Высокая | ✅ Высокая |
| Простота продакшена | ✅ Средняя | ⚠️ Высокая (своя обвязка) |
| Соответствие SOC 2 | ✅ Аудируемое хранилище | ⚠️ In-memory, нет аудит-лога |

### 3.4 Итоговый выбор векторной БД

**Рекомендация: ChromaDB.**

Обоснование:
1. **Инкрементальные обновления** критичны при 400 новых страницах в месяц и CI/CD-интеграции для автоматической индексации свежей документации.
2. **Хранение метаданных** (источник, дата, версия, владелец) необходимо для выявления пробелов в документации — одной из бизнес-целей проекта.
3. **SOC 2 совместимость** — ChromaDB с PostgreSQL-бэкендом обеспечивает аудируемое персистентное хранилище, в отличие от FAISS, живущего в оперативной памяти.
4. **Микросервисная готовность** — REST API позволяет вынести векторный поиск в отдельный сервис, что соответствует целевой архитектуре QuantumForge на AWS EKS.

## 4. Рекомендуемая конфигурация сервера

Для MVP с локальным стеком (эмбеддинги + ChromaDB + LLM Mistral 7B):

| Компонент | Базовая конфигурация | Оптимальная конфигурация |
|-----------|---------------------|--------------------------|
| **CPU** | 8 vCPU | 16 vCPU |
| **RAM** | 32 ГБ (из них ~8 ГБ под LLM Q4) | 64 ГБ (запас под рост индекса и кеширование) |
| **GPU** | Опционально: NVIDIA T4 16 ГБ | NVIDIA A10 24 ГБ или A100 40 ГБ |
| **Storage** | 200 ГБ NVMe SSD | 500 ГБ NVMe SSD |
| **OS** | Ubuntu 22.04 LTS | Ubuntu 22.04 LTS |
| **Контейнеризация** | Docker Compose | Kubernetes (EKS) |

**Расчёт:**
- **ChromaDB индекс** (100 000 чанков × 1024-dim эмбеддинга): ~400 МБ + HNSW-граф ~1–2 ГБ.
- **LLM Mistral 7B Q4:** ~4–5 ГБ RAM.
- **Мультиязычные эмбеддинги e5-large:** ~2 ГБ RAM.
- **OS и служебные процессы:** ~4 ГБ.
- **Итого RAM:** ~12–15 ГБ — достаточно 32 ГБ с запасом.
- **GPU:** Для LLM инференса T4 достаточно для Q4-модели (batch size 1–4), для переиндексации больших объёмов ускоряет в 5–10 раз.

## 5. Итоговые варианты архитектуры

### Вариант 1. Полностью локальный стек (Рекомендуемый)

**Состав:**
- **LLM:** Mistral 7B Q4 через Ollama (CPU) или vLLM (GPU)
- **Эмбеддинги:** `intfloat/multilingual-e5-large` (локально)
- **Векторная БД:** ChromaDB + PostgreSQL
- **Развёртывание:** Docker Compose (MVP) → Kubernetes EKS (продакшен)

**Плюсы:**
- Полный контроль над данными — SOC 2/GDPR compliance.
- Предсказуемая стоимость, не зависящая от объёма запросов.
- Архитектура масштабируется на всю компанию и внешних клиентов.
**Минусы:**
- Нужна экспертиза для развёртывания и поддержки.
- Стартовые затраты на сервер при использовании GPU.

### Вариант 2. Гибридный стек с Azure OpenAI

**Состав:**
- **LLM:** Azure OpenAI GPT-4o в EU-тенанте
- **Эмбеддинги:** Sentence-Transformers локально
- **Векторная БД:** ChromaDB
- **Развёртывание:** Kubernetes EKS + Azure API

**Плюсы:**
- Минимальная экспертиза по LLM, эталонное качество ответов.
- Данные эмбеддингов и векторная БД остаются в контуре компании.
**Минусы:**
- Зависимость от Microsoft Azure, необходимость DPA.
- Рост стоимости при масштабировании.
- Запросы с контекстом уходят в облако — риск для сверхчувствительных документов.

### Вариант 3. Минимальный MVP (временное решение)

**Состав:**
- **LLM:** OpenAI API (для прототипирования)
- **Эмбеддинги:** Sentence-Transformers локально
- **Векторная БД:** FAISS (in-memory)
- **Развёртывание:** Один Docker-контейнер

**Плюсы:**
- Максимально быстрый старт (1–2 дня до работающего прототипа).
- Минимум зависимостей.
**Минусы:**
- Непригоден для продакшена (конфиденциальность, инкрементальные обновления).
- Только для демонстрации концепции внутренней команде.

### Вариант 4. Корпоративный on-premise

**Состав:**
- **LLM:** Llama 3 70B Q4 (GPU-сервер) или Mistral Large
- **Эмбеддинги:** `multilingual-e5-large`
- **Векторная БД:** ChromaDB с PostgreSQL на выделенном сервере
- **Оркестрация:** LangChain/LlamaIndex, мониторинг Prometheus + Grafana

**Плюсы:**
- Изолированная среда без внешних зависимостей.
- Высокая производительность.
- Полный аудит-лог для SOC 2 Type II.
**Минусы:**
- Высокие стартовые затраты на инфраструктуру.
- Избыточен для MVP.

## 6. Финальная рекомендация

**Рекомендуемый стек для QuantumForge Software:**

| Компонент | Выбор | Причина |
|-----------|-------|---------|
| **LLM** | Mistral 7B Q4 (Ollama) | Контроль данных, достаточное качество для RAG, низкие требования к инфраструктуре |
| **Эмбеддинги** | `intfloat/multilingual-e5-large` | Мультиязычность (англ., фин., швед., эст.), лидер бенчмарков, локально |
| **Векторная БД** | **FAISS** (IndexFlatIP) | Экстремально быстрый поиск, минимум зависимостей, простота развёртывания, персистентность через `faiss.write_index` |
| **Фреймворк RAG** | LangChain / LlamaIndex | Абстракция над LLM и векторной БД, лёгкая замена компонентов |
| **Инфраструктура MVP** | 16 vCPU, 64 ГБ RAM, 500 ГБ NVMe, Docker Compose | |
| **Целевая инфраструктура** | AWS EKS, GPU-нода (A10) | |

**Почему FAISS:**
FAISS обеспечивает экстремально быструю скорость поиска за счёт прямого доступа к памяти, минимальные зависимости (только `faiss-cpu` + `numpy`), простоту развёртывания без дополнительных сервисов. Для MVP с объёмом до 100 000 чанков IndexFlatIP обеспечивает точный поиск без аппроксимации. Метаданные хранятся в отдельном JSON-файле рядом с индексом. При масштабировании возможен переход на IndexIVF для ускорения поиска или на ChromaDB для встроенного управления метаданными.

**Дорожная карта:**
1. **Неделя 1–2:** MVP на Docker Compose (Mistral 7B + e5-large + FAISS), индексация 1000 документов.
2. **Неделя 3–4:** Подключение полной базы, тестирование качества retrieval (recall@k, MRR), тонкая настройка чанкинга.
3. **Месяц 2:** Миграция на EKS, подключение CI/CD для автоматической индексации обновлений, внедрение мониторинга.
4. **Месяц 3:** Пилот с реальными пользователями, сбор метрик времени поиска, выявление пробелов, итеративное улучшение.
