# Задание 7. Аналитика покрытия и качества базы знаний

## Цель

Оценить полноту и актуальность базы знаний, выявить темы, по которым бот не сможет дать ответы, и обоснованно улучшить покрытие.

## Методология

### 1. Искусственные пробелы

Из базы знаний удалены 3 ключевые сущности разных типов:

| # | Сущность | Тип | Файл | Размер | Перекрёстные ссылки |
|---|----------|-----|-------|--------|---------------------|
| 1 | Rift of Echoes | место | `Rift_of_Echoes.txt` | 17 строк | ~10 файлов |
| 2 | Valdric | персонаж | `Valdric.txt` | 238 строк | ~20 файлов (~139 упоминаний) |
| 3 | The Duskborne Purge | событие | `The_Duskborne_Purge.txt` | 28 строк | ~10 файлов (~25 упоминаний) |

**Обоснование выбора:**

- **Rift of Echoes** — ключевая локация, где произошли две битвы Toren vs Kaelen и битва Hashirama vs Theron. Небольшой файл, но важный для понимания географии и истории мира.
- **Valdric** — один из Трёх Легенд, наставник главного героя Toren Solwind. Крупный файл с обширными перекрёстными ссылками в ~20 других файлах.
- **The Duskborne Purge** — ключевое событие (массовое уничтожение клана Duskborne), определившее судьбу нескольких персонажей. Средний файл с умеренными перекрёстными ссылками.

**Отвергнутые кандидаты:**
- **The Obsidian Circle** — 225 перекрёстных ссылок, слишком центральная сущность. Удаление создало бы массивные, очевидные пробелы.
- **Zephros** — 120+ перекрёстных ссылок, аналогично слишком перvasive.

### 3. Метрики оценки

- **Keyword Coverage** — доля ожидаемых ключевых слов, найденных в ответе (0–100%)
- **Refusal Rate** — доля запросов, на которые бот отказался отвечать
- **Retrieval Hit Rate** — доля запросов, где FAISS нашёл чанки из целевого файла
- **Avg Score** — средний cosine similarity score найденных чанков

## Анализ и выводы

### 1. Влияние пробелов на Retrieval

**Retrieval hit rate для gap-запросов: 0% → 100%** — это самый значимый результат. При удалении файлов сущностей FAISS не может найти ни одного чанка из целевого файла (файл физически отсутствует). После восстановления все запросы находят целевые документы.

Это подтверждает, что FAISS-индекс корректно работает и находит релевантные документы при их наличии.

### 2. Эффект перекрёстных ссылок

Keyword coverage для gap-запросов снизился умеренно (63.4% → 70.1%, Δ=+6.7%). Это объясняется тем, что удалённые сущности упоминаются в других файлах KB:

- **Rift of Echoes** упоминается в `Toren_Solwind.txt`, `Kaelen_Duskborne.txt`, `Theron_Duskborne.txt` и др. — бот смог собрать информацию из перекрёстных ссылок (G1: 85.7% даже без файла).
- **Valdric** упоминается в ~20 файлах — информация о нём частично доступна через файлы учеников (G3: 71.4%, G4: 100%).
- **The Duskborne Purge** упоминается в `Soren_Duskborne.txt`, `Kaelen_Duskborne.txt` и др. — но ключевые детали (кто именно и почему) были утеряны (G5: 40%).

### 3. Refusal Rate

Refusal rate для gap-запросов: **33.3% → 0.0%**. Два запроса (G2, G6) вызвали отказ бота при наличии пробелов. Это показывает, что бот корректно определяет недостаток информации и честно сообщает об этом, а не выдумывает факты.

### 4. Влияние на контрольные запросы

Control-запросы показали неожиданное улучшение coverage (72.5% → 85.0%, Δ=+12.5%). Это объясняется:
- Запрос C3 (Вердания) улучшился с 50% до 100% — при полной KB FAISS находит более релевантные чанки, т.к. индекс содержит больше документов.
- Удаление файлов изменило распределение чанков в индексе, что повлияло на ранжирование результатов.

### 5. Рекомендации по улучшению покрытия

1. **Добавить перекрёстные ссылки** — для ключевых сущностей добавить явные упоминания в связанных файлах, чтобы при удалении одного файла информация оставалась доступной.
2. **Увеличить chunk_overlap** — текущий overlap (150 символов) может быть недостаточен для сохранения контекста между чанками.
3. **Добавить summary-чанки** — для каждого файла создать краткое резюме, которое будет содержать ключевые факты и связи с другими сущностями.
4. **Мониторинг coverage** — регулярно запускать golden set тесты для отслеживания деградации качества при обновлениях KB.

## Логирование запросов

Каждый запрос к RAG-боту (через CLI, Telegram или тесты) автоматически сохраняется в JSONL-лог `Task4/logs/query_log.jsonl`.

### Формат записи

```json
{
  "timestamp": "2026-06-13T13:45:23.291118+00:00",
  "query": "Who is Toren Solwind?",
  "chunks_found": 5,
  "has_chunks": true,
  "answer_length": 1062,
  "is_success": true,
  "sources": ["Elara Moonvane", "Kaelen Duskborne", "Toren Solwind"],
  "elapsed_sec": 58.98
}
```

### Поля

| Поле | Тип | Описание |
|------|-----|----------|
| `timestamp` | string | Время запроса в ISO 8601 UTC |
| `query` | string | Текст запроса пользователя |
| `chunks_found` | int | Количество найденных чанков в FAISS |
| `has_chunks` | bool | Были ли найдены чанки |
| `answer_length` | int | Длина ответа LLM в символах |
| `is_success` | bool | Флаг успешного ответа (есть чанки, ответ >50 символов, нет отказа/ошибки) |
| `sources` | list | Список файлов-источников из KB |
| `elapsed_sec` | float | Время обработки запроса в секундах |

### Критерии успешности (`is_success`)

Ответ считается успешным, если выполнены все условия:
1. Найден хотя бы один чанк в FAISS
2. Длина ответа > 50 символов
3. Ответ не содержит маркеров отказа («не нашёл», «no information» и т.д.)
4. Ответ не начинается с ❌ (ошибка подключения к Ollama)

### Реализация

Логирование встроено в метод `_log_query()` класса `RAGEngine` в `Task4/rag_engine.py`. Лог-файл создаётся автоматически при первом запросе в `Task4/logs/query_log.jsonl`. Записи добавляются в режиме append — лог не перезаписывается.
